## 2. Before creating a mailbox, get the site settings

### 2.1 Get settings

Preferred endpoint:

```http
GET /open_api/settings
```

Fallback endpoint:

```http
GET /api/settings
```

The client probes them in this order.

Implementation:

- `lib\api.ts:304`
- `lib\api.ts:317`

### 2.2 Fields that matter most

```json
{
  "domains": ["example.com"],
  "defaultDomains": ["example.com"],
  "domainLabels": ["Main domain"],
  "randomSubdomainDomains": ["example.com"],
  "enableAddressPassword": true,
  "enableCreateAddressSubdomainMatch": false,
  "cfTurnstileSiteKey": "...",
  "needAuth": false
}
```

Field notes:

- `domains`: the currently recommended domain list
- `defaultDomains`: used as a fallback if `domains` is empty
- `domainLabels`: display names for the domains
- `randomSubdomainDomains`: root domains that allow "random subdomain" mode
- `enableAddressPassword`: whether a new mailbox may return an address password
- `enableCreateAddressSubdomainMatch`: related to the subdomain creation policy; whether matching is strict is decided by the server
- `cfTurnstileSiteKey`: mainly for human verification during web frontend sign-up/verification; not required for receiving mail

Tests also verify that:

- `/open_api/settings` is preferred
- `defaultDomains` is used when `domains` is empty
- `/api/settings` is used when `/open_api/settings` does not exist

Tests:

- `lib\__tests__\api.test.ts:190`
- `lib\__tests__\api.test.ts:223`
- `lib\__tests__\api.test.ts:253`

## 3. Mailbox creation endpoints

## 3.1 Regular creation

```http
POST /api/new_address
```

Request body:

```json
{
  "name": "alice",
  "domain": "example.com",
  "enablePrefix": true,
  "enableRandomSubdomain": false
}
```

Response:

```json
{
  "jwt": "<address-jwt>",
  "address": "prefix.alice@example.com",
  "address_id": 123,
  "password": "optional-password"
}
```

Implementation:

- `lib\api.ts:339`

## 3.2 Admin creation

```http
POST /admin/new_address
```

The request body is the same as regular creation, but this header is required:

```http
x-admin-auth: <adminPassword>
```

Client logic: whenever an admin password is configured, it uses `/admin/new_address`.

Implementation:

- `lib\api.ts:353`

## 3.3 Response fields

- `jwt`: the most important field; you need it to fetch this mailbox's inbox later
- `address`: the address the server actually created; **always rely on it, especially in random subdomain mode**
- `address_id`: useful in admin mode to look up credentials / list addresses with admin endpoints
- `password`: only returned by some server configurations

Type definition:

- `lib\api.ts:114`

## 4. Three ways to create a mailbox

## 4.1 Subdomain mailbox

### How to call it

The client builds the final `domain` as:

```text
<subdomainPrefix>.<selectedDomain>
```

and then submits:

```json
{
  "name": "alice",
  "domain": "sub.example.com",
  "enablePrefix": true,
  "enableRandomSubdomain": false
}
```

UI logic:

- `app\(tabs)\addresses.tsx`
- `app\admin.tsx`

Equivalent in a script:

```js
domain = `${subdomainPrefix}.${selectedDomain}`;
```

### Example

```json
{
  "name": "order",
  "domain": "otp.example.com",
  "enablePrefix": true,
  "enableRandomSubdomain": false
}
```

Possible result:

```json
{
  "address": "prefix.order@otp.example.com",
  "jwt": "..."
}
```

---

## 4.2 Random subdomain mailbox

### Prerequisite

Check this field in the `/open_api/settings` response:

```json
"randomSubdomainDomains": ["example.com"]
```

The client only treats a root domain as supporting random subdomains if it appears in this list.

### How to call it

```json
{
  "name": "alice",
  "domain": "example.com",
  "enablePrefix": true,
  "enableRandomSubdomain": true
}
```

### Important

The random subdomain is generated by the server, not by the client, so:

- **Do not assume the final address yourself**
- Always use the returned `address`

For example, if the request is:

```json
{
  "name": "alice",
  "domain": "example.com",
  "enableRandomSubdomain": true
}
```

the response might be:

```json
{
  "address": "prefix.alice@x8f2k.example.com",
  "jwt": "..."
}
```

---

## 4.3 Custom domain mailbox

There are two interpretations:

### A. Custom username + one of the available domains

This is the client's standard mode:

```json
{
  "name": "myname",
  "domain": "example.com",
  "enablePrefix": false,
  "enableRandomSubdomain": false
}
```

### B. A script passes its own custom domain

In the current client, `domain` is just a string in the request body, and the frontend does **no extra strict validation**.

So in theory a script can POST directly:

```json
{
  "name": "alice",
  "domain": "mail.custom-domain.com",
  "enablePrefix": false,
  "enableRandomSubdomain": false
}
```

However:

- whether creation is allowed
- whether the domain must be on the `settings.domains` allowlist
- whether `enableCreateAddressSubdomainMatch` applies

are all **decided by the server**.

### Recommendation

For a scripted product, use two levels:

1. **Safe mode**: only allow domains listed in `settings.domains` / `defaultDomains`
2. **Forced mode**: let the caller enter `domain` manually, and surface server failures as they are

## 5. Getting a mailbox JWT / credential

### 5.1 Get it at creation time

Recommended. The `/api/new_address` or `/admin/new_address` response already contains it:

```json
{
  "jwt": "...",
  "address": "..."
}
```

### 5.2 Verify an existing credential

```http
POST /open_api/credential_login
```

Request:

```json
{
  "credential": "<jwt>"
}
```

You can keep using the same JWT afterwards.

Implementation:

- `lib\api.ts:399`

### 5.3 Exchange an existing email + password for a JWT

```http
POST /api/address_login
```

Request body:

```json
{
  "email": "prefix.alice@example.com",
  "password": "<sha256(password)>"
}
```

Note:

- The client hashes the password with SHA-256 before sending it

Implementation:

- `lib\api.ts:410`

### 5.4 Admin: get credentials by addressId

```http
GET /admin/show_password/{addressId}
```

Response:

```json
{
  "jwt": "...",
  "password": "optional",
  "address": "prefix.alice@example.com"
}
```

Implementation:

- `lib\api.ts:845`

## 6. Receiving mail / fetching verification codes

## 6.1 User inbox endpoint

```http
GET /api/mails?limit=<n>&offset=<n>
```

Required headers:

```http
Authorization: Bearer <jwt>
x-user-token: <jwt>
```

Implementation:

- `lib\api.ts:431`

Two response formats are supported:

### Old/simple format

```json
[
  {
    "id": 1,
    "source": "...",
    "raw": "...",
    "created_at": "2026-04-24T12:00:00Z",
    "address": "prefix.alice@example.com",
    "subject": "Verification code",
    "metadata": "{...}"
  }
]
```

### Standard paginated format

```json
{
  "results": [
    {
      "id": 1,
      "source": "...",
      "raw": "...",
      "created_at": "2026-04-24T12:00:00Z",
      "address": "prefix.alice@example.com",
      "subject": "Verification code",
      "metadata": "{...}"
    }
  ],
  "count": 1
}
```

The client normalizes both formats.

Definitions and normalization:

- `lib\api.ts:24`

## 7. Parsing mail and extracting verification codes

## 7.1 Mail parsing

The client parses, in order of preference:

- `raw`
- otherwise `source`

It runs MIME / RFC822 parsing and produces:

- `subject`
- `from`
- `to`
- `text`
- `html`
- `date`
- `attachments`

Implementation:

- `lib\mail-parser.ts:747`

## 7.2 Body text priority

When getting the body text, the priority is:

1. `mail.text`
2. `mail.html` converted to plain text
3. `mail.raw`

Implementation:

- `lib\mail-parser.ts:652`

## 7.3 Verification code extraction priority

The client extracts verification codes as follows:

### First priority: `metadata.ai_extract`

If the metadata contains:

```json
{
  "ai_extract": {
    "type": "auth_code",
    "result": "913245"
  }
}
```

that result is used directly.

Implementation:

- `lib\mail-parser.ts:868`
- `lib\mail-parser.ts:899`

Tests:

- `lib\__tests__\mail-parser.test.ts:231`

### Second priority: regex match on body / subject

The main patterns are:

#### Chinese

Matches the Chinese words for "verification code", "check code", "dynamic code", "dynamic password", "login code" and "security code", optionally followed by "is" or a colon, then the code. In the source the Chinese words are written as `\uXXXX` escapes:

```regex
(?:\u9a8c\u8bc1\u7801|\u6821\u9a8c\u7801|\u52a8\u6001\u7801|\u52a8\u6001\u5bc6\u7801|\u9a8c\u8bc1\u4ee3\u7801|\u767b\u5f55\u7801|\u5b89\u5168\u7801)\s*(?:\u662f|\u4e3a|:|\uff1a)?\s*([A-Z0-9]{4,8})
```

#### English

```regex
(?:verification code|security code|one[- ]?time code|login code|passcode|otp)(?:\s+is|\s*[:\uff1a-])\s*([A-Z0-9]{4,8})
```

### Third priority: keyword + candidate code fallback

If the subject/body contains:

- the Chinese word for "verification code"
- `verification`
- `security code`
- `otp`

the client searches the full text for:

```regex
\b[A-Z0-9]{4,8}\b
```

and prefers candidates that contain digits.

## 8. The two recommended flows for scripts

## 8.1 Option A: save the JWT at creation (simplest)

1. `GET /open_api/settings`
2. `POST /api/new_address`
3. Save the returned:
   - `address`
   - `jwt`
   - `address_id`
   - `password`
4. Poll:
   - `GET /api/mails?limit=20&offset=0`
5. Run MIME parsing on the latest mail
6. Check `metadata.ai_extract` first
7. Then extract the code with the body regex

### Advantages

- Shortest flow
- No admin password needed
- Each mailbox is independent

## 8.2 Option B: central admin mode

1. `GET /open_api/settings`
2. `POST /admin/new_address`
3. Save the returned `address` / `address_id`
4. If you need the credentials later:
   - `GET /admin/show_password/{addressId}`
5. To receive mail, call directly:
   - `GET /admin/mails?limit=20&offset=0&address=<email>`

### Advantages

- No need to maintain a JWT per mailbox
- Suitable for batch scripts / backend systems

## 9. Things to watch when implementing a script

1. **Always fetch settings first**
   - To get `domains`
   - To check `randomSubdomainDomains`

2. **For random subdomains, rely on the returned address**
   - Do not build the final address yourself

3. **Support both inbox response formats**
   - `[]`
   - `{ results, count }`

4. **Do not look only at `subject`**
   - Many verification codes are only in the `text/html` body

5. **Keep metadata**
   - If the server already ran `ai_extract`, reusing it is the most reliable

6. **If you use admin endpoints**
   - `x-admin-auth` takes the raw admin password, not a hash

7. **If you use `/api/address_login`**
   - Hash the password with SHA-256 first

## 10. Extra: web-side endpoints visible in the official frontend bundle

In `frontend\assets\Admin-DL1NEMu-.js` there is also a set of web user endpoints, for example:

- `/user_api/verify_code`
- `/user_api/register`
- `/user_api/login`
- `/user_api/mails`

These are aimed more at **website user sign-up / sign-in / the web mailbox page**.

If your product is "create mailboxes automatically and poll for verification codes", prefer the main flow described here:

- `/open_api/settings`
- `/api/new_address` / `/admin/new_address`
- `/api/mails` / `/admin/mails`

because this flow is the clearest and most stable in the current mobile source.
